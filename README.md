# UPI Growth Analytics & Fraud Detection

**Python · SQL · Statistics · XGBoost**

Two halves of the same payments-product question: **which users drive retention and lifetime value, and how do
we keep fraud out without hurting them?**

| Part | Data | Methods |
|---|---|---|
| Growth analytics | Simulated UPI platform: 100,000 users, 18 months, 1.3M transactions | SQL marts, cohort retention, funnel, CLV, RFM, logistic regression |
| A/B testing | 3 experiments, 63K participants (inside the simulation) | power analysis, SRM check, z / Welch tests, Holm correction, decision rules |
| Fraud detection | **IEEE-CIS (Vesta): 590,540 real transactions**, 3.5% fraud | time-based split, feature engineering, XGBoost, imbalance handling, PR-AUC, cost-based threshold, SHAP |

## Key results

**Growth** ([full report](reports/growth_report.md))
- A **merchant payment in the first week** is the activation moment: **43.9% vs 16.6%** of users still active at
  month 6, and **3.0x** the odds of day 30-60 retention after controlling for channel, city tier, device and age.
- **Referral users are worth 2.7x paid users**: 24-month CLV of Rs 32.7 vs Rs 12.0 per KYC user.
- **The top 20% of users generate 67% of revenue**; "Champions" are 24% of users and 61% of revenue.
- The largest funnel leak is activation: 83% complete KYC, only 28% pay a merchant in week 1.

**A/B testing** ([full report](reports/abtest_report.md))

| Experiment | Primary metric | Result (95% CI) | Decision |
|---|---|---|---|
| First-merchant cashback | 7-day activation | **+5.9 pts** (+4.6 to +7.2), 27.5% → 33.4% | Ship |
| Simplified KYC flow | KYC completion | **+2.6 pts** (+1.6 to +3.5) | Ship |
| Referral nudge banner | transactions in first 30 days | −0.02 (−0.12 to +0.08) | Don't ship |

Every planted true effect falls inside the estimated confidence interval (see *Validation* below).

**Fraud detection** ([full report](reports/fraud_report.md), generated by `make fraud`)
- PR-AUC, recall/precision at a cost-optimal threshold, share of fraud dollars stopped, and genuine customers
  blocked per 100 frauds caught, all on a held-out *future* time period.

## Why simulate the growth data?

No public dataset has user-level UPI behaviour, since payment companies don't release it. So the growth side
**simulates** a platform with *known* behaviours planted in it ([`src/upi/simulate.py`](src/upi/simulate.py)):
referral users are more engaged, activation cuts churn, the cashback test has a +6pt effect, the banner has none.

That turns a weakness into a test of method: **the analysis never reads the simulator's parameters**. It has to
rediscover each effect from raw tables using SQL and statistics, and we can check whether it got the right answer:

| Planted effect | Planted | Estimated | 95% CI | Recovered? |
|---|---|---|---|---|
| Cashback → activation | +6.28 pts | +5.89 pts | +4.62 to +7.17 | yes |
| KYC flow → KYC completion | +2.54 pts | +2.55 pts | +1.61 to +3.49 | yes |
| Banner → transactions | 0 | −0.02 | −0.12 to +0.08 | yes (null) |
| Activation → retention | strong | OR 3.0 | 2.9 to 3.2 | yes |
| Device / age → retention | none | OR ≈ 1.0 | not significant | yes |

The fraud side uses **real** data because realistic fraud can't be faked.

```bash

make test

```

1. Kaggle → *Settings* → *API* → **Create New Token**, then save `kaggle.json` to `~/.kaggle/`.


## Methodology highlights

**SQL**
- A modelled analytics layer (`fct_transactions`, `fct_user_months`, `user_metrics`) built with CTEs, window
  functions (`LAG`, running sums) and a recursive CTE.
- **Right-censoring guard:** a user only counts towards month-*k* retention or a 60-day metric if they're old enough
  to have been observed. Without this, recent cohorts drag every curve down.

**Statistics**
- Sample size from the pre-period baseline, MDE and 80% power; achieved power reported after the test.
- Sample-ratio-mismatch check (χ², p < 0.001) before reading any result.
- Pooled z-test for proportions, Welch t-test plus Mann-Whitney for counts, Holm correction across metrics.
- Pre-registered primary metric. The report flags a secondary metric that came out "significant" under a true null,
  which is exactly why the decision rests on the primary.
- Tests verify the type-I error rate (~5% on simulated A/A tests) and CI coverage.

**Fraud modelling**
- **Time-based split.** Random splits leak future card behaviour and inflate scores.
- Features fitted on the training period only: approximate user ID (`card1 + addr1 + first-seen day`),
  amount-vs-usual ratios, frequency encodings, cents (foreign-currency signal), email-domain match, time of day.
- Imbalance: class weights vs undersampling vs none, compared on validation PR-AUC. No SMOTE, because interpolated
  rows across anonymised, sparse columns aren't realistic transactions.
- **PR-AUC** as the headline metric. **Threshold chosen by cost** (missed fraud = amount lost; false decline = $10
  friction) on validation, then frozen for test.
- Production framing: approve / step-up (OTP) / block bands.

## Limitations

- Growth data is simulated. Findings show the *method* works; real-world effect sizes would differ.
- The CLV tail beyond month 12 is extrapolated.
- IEEE-CIS is card-not-present e-commerce, not UPI; anonymised features limit interpretation.

## Resume bullets

- Analysed a simulated UPI platform of 100K users over 18 months with SQL (CTEs, window functions) and Python;
  found that a first-week merchant payment triples the odds of retention (43.9% vs 16.6% month-6 retention) and that
  referral users carry 2.7x the 24-month CLV of paid users.
- Designed and analysed 3 A/B tests (power analysis, SRM checks, Holm-corrected z / Welch tests); recommended
  shipping first-payment cashback (+5.9 pts activation, p < 0.001) and rejected a referral banner with no effect.
- Built an XGBoost fraud model on 590K+ real transactions with a time-based split, leakage-free feature engineering
  and class-imbalance handling; chose the decision threshold by business cost to balance fraud losses against
  false declines.
